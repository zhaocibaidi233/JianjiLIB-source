# 升级与回滚手册

> 面向现场运维人员。升级前请完整阅读本文，并按第 1 节逐项确认。

---

## 1. 升级前检查

按顺序完成以下六项，每一项都应看到明确的成功结果后再继续。

### 1.1 停止服务

通过启动器的「停止服务」按钮停止后端；如使用命令行启动，请结束监听服务端口的进程。

### 1.2 备份数据库并校验

```bat
if not exist backups mkdir backups
runtime\pgsql\bin\pg_dump.exe -h 127.0.0.1 -p 55432 -U postgres -Fc jianji > backups\jianji_升级前_YYYYMMDD.dump
runtime\pgsql\bin\pg_restore.exe -h 127.0.0.1 -p 55432 -l backups\jianji_升级前_YYYYMMDD.dump > nul && echo 备份可读
```

内置数据库模式使用便携包内的 `runtime\pgsql\bin`；外部 PostgreSQL 模式可以改用系统安装的 `pg_dump`/`pg_restore`。

注意事项：

- 示例库名 `jianji` 仅作演示，请替换为实际库名。启动器运行页会显示「实际库：host:port/db」，以该信息为准。
- Windows 默认安装不会把 PostgreSQL 的 `bin` 目录加入 `PATH`。如提示找不到命令，请先进入安装目录，例如：

```bat
cd /d "C:\Program Files\PostgreSQL\18\bin"
```

- 只执行 `pg_dump` 而不校验，无法确认备份文件是否完整。`pg_restore -l` 能列出备份内容即表示文件可读。
- `init_db.py` 与启动器的「初始化当前库」在升级已有非空库前会自动执行 `pg_dump -Fc` 并校验，但手工整库备份仍建议保留。

### 1.3 复制当前程序目录

将整个程序目录复制为 `Jianji-backup-YYYYMMDD`。请复制完整目录，而不是只复制 `backend/app`；出现问题时整目录换回最直接。

### 1.4 保存启动器配置

另存 `launcher-config.json`，其中包含端口、局域网开关与数据库连接设置。

### 1.5 记录当前版本

记录界面或日志中的版本号，并执行：

```bash
cd backend && alembic current
```

将结果写入运维记录，回滚时用于确认目标版本。

### 1.6 确认没有后台任务

确认没有正在执行的导入、盘点、批量注销等后台任务。数据库还原会丢失升级开始后产生的数据。

## 2. 升级步骤

1. 用新便携包覆盖 `runtime/`、`backend/app`、`backend/migrations`、`backend/scripts`、`backend/requirements.lock.txt`、`backend/requirements-mcp.lock.txt`、`frontend/dist`、根目录的 `VERSION`、`README.md`、`.env.example`、`JianjiLauncher.exe`，以及 `docs/`。
2. **保留 `data/` 整个目录**（`pgdata/`、`launcher-config.json`），以及 `launcher-logs/`、`backups/`。内置数据库模式不要删除或替换 `data/pgdata`；外部 PostgreSQL 模式如仍使用 `backend/.venv` 也保留。
3. 依赖由便携包内置的 `runtime/` 固定，内置数据库模式不需要执行 `pip install`。只有外部 Python 模式才需要：
   ```bat
   cd backend
   .venv\Scripts\python.exe -m pip install -r requirements.lock.txt
   ```
4. 升级数据库结构。内置数据库模式使用内置 Python：
   ```bat
   runtime\python\python.exe -m alembic -c backend\alembic.ini upgrade head
   ```
   外部 Python 模式仍使用 `backend\.venv\Scripts\python.exe -m alembic upgrade head`（工作目录 `backend`）。

> PostgreSQL 主版本变化时，不要直接用新运行时启动旧 `data/pgdata`。先停止服务并备份整个 `data/`，用旧运行时导出，再在新数据目录初始化后恢复；启动器检测到主版本不一致会拒绝启动。

5. 前端无需单独构建。`frontend/dist` 已由便携包提供，由后端以单端口方式托管。
6. 启动服务并完成以下冒烟检查：
   - `curl http://127.0.0.1:8000/api/health` 返回 `{"status":"ok","db":true,...}`；
   - 使用管理员账号登录；
   - 打开书目列表，确认数据可正常读取。

## 3. 回滚

按影响范围选择最小动作。

| 情形 | 动作 | 数据库 | 预计耗时 |
| --- | --- | --- | --- |
| 前端异常（白屏、按钮无响应） | 将 `frontend/dist` 换回备份目录中的版本，重启服务 | 不动 | 约 3 分钟 |
| 后端异常（500、启动失败） | 将 `backend/app` 换回备份目录中的版本，重启服务 | 不动 | 约 3 分钟 |
| 迁移已执行、表结构变化导致业务异常 | 停止服务，整目录换回 `Jianji-backup-YYYYMMDD`，整库还原，启动 | 还原 | 15–30 分钟 |
| 数据被误写或误删 | 整库还原到事发前最近的备份 | 还原 | 15–30 分钟 |

整库还原会清空目标库，执行前必须确认库名：

```bat
runtime\pgsql\bin\pg_restore.exe -h 127.0.0.1 -p 55432 -U postgres -d jianji --clean --if-exists ^
  backups\jianji_升级前_YYYYMMDD.dump
```

## 4. 两个容易误判的地方

### 4.1 `pg_restore` 的退出码需要结合命令判断

- 使用 `--if-exists` 时，空库与非空库都会返回 0，标准错误通常没有输出。
- 不使用 `--if-exists` 时，`pg_restore` 会尝试删除一批并不存在的对象，产生大量「关系不存在」提示并返回 1；但数据可能已经完整还原。

判断还原是否成功应以数据为准：

```bash
psql -U postgres -d jianji -c "select count(*) from records;"
psql -U postgres -d jianji -c "select count(*) from holdings;"
```

建议始终使用 `--if-exists`，避免无意义的错误输出。

### 4.2 `alembic downgrade` 不是回滚工具

`alembic downgrade base` 会逐条撤销迁移，最终删除全部业务表。它适合在测试库验证迁移链，不能作为生产回滚手段。生产回滚应使用「整目录换回 + 整库还原」，因为迁移只能还原结构，无法还原数据。

个别迁移的降级还会因数据约束失败。例如，当库中存在跨图书库的同号读者账号时，重建唯一索引会触发 `UniqueViolation`。此时事务会回滚，`alembic current` 仍显示原版本，不会留下半降级状态，但也无法继续降级。遇到这种情况应直接执行整库还原。

## 5. 上线前演练

在非生产库上完整执行一次：

1. 备份；
2. 升级；
3. 修改一条测试数据；
4. 整库还原；
5. 核对主要数据表的记录数。

记录实际耗时，作为正式升级窗口的参考。演练库不得使用生产库或真实学校数据。

## 6. 部署注意事项

### 6.1 备份文件包含敏感信息

数据库备份可能包含套录源配置、读者信息与借阅记录。请按以下方式保管：

1. 备份目录的访问控制只授予管理员，不要放在共享盘、网盘同步目录或即时通讯工具中；
2. 交付包与备份分开保存，不要将 `.dump` 或 `backups/` 一并交付给学校或第三方；
3. 换机、送修、外包巡检前，确认备份文件的位置与可读范围；
4. 必要时使用磁盘加密或加密压缩保护备份文件；
5. 便携包使用 22 个中图法一级大类；分类号可直接录入，或由 Z39.50 套录带入。详见便携包根目录的 `DATA_NOTICE.md`。

### 6.2 使用独立的业务数据库账号

建议为业务运行创建独立账号，只授予当前数据库所需的增删改查权限；数据库迁移使用单独账号，或由运维人员临时切换，不要长期使用高权限账号。

### 6.3 外部数据源权限应受控

系统支持配置 Z39.50 与外部 PostgreSQL 套录源。相关配置权限建议只授予网络管理员或馆长；如需限制服务器可访问的地址范围，可在网络层只放行实际使用的目标地址与端口。

### 6.4 正式部署使用构建产物

正式部署请确认包内包含 `frontend/dist`，由后端以单端口方式托管。`frontend/dist` 不存在时，启动器会进入开发模式，仅适合本机调试。

### 6.5 日志与数据导出

日志与操作记录可能包含读者、借阅与操作信息。打包外发或共享前，请按学校数据管理规范处理。

## 7. 首次运行与 SmartScreen

`JianjiLauncher.exe` 当前未使用代码签名证书。首次运行时，Windows 可能显示「Windows 已保护你的电脑」或「未知发布者」提示。

- 可点击「更多信息」→「仍要运行」继续；
- 学校批量部署时，可在组策略中把程序目录加入受信任位置；
- 也可以使用自签名证书，但每台电脑仍需手动导入证书，否则仍会提示；
- 提示「未知发布者」不代表文件损坏，文件是否可信应依据交付包来源与校验和判断。

## 8. 非 Windows 部署（Linux / macOS）

当前图形化数据库管理功能位于 Windows 启动器中，Linux 与 macOS 只提供命令行方式。

```bash
cd backend
python -m venv .venv && . .venv/bin/activate
pip install --no-deps -r requirements.lock.txt -r requirements-mcp.lock.txt

export JIANJI_DATABASE_URL='postgresql+psycopg2://用户:口令@localhost:5432/jianji'
python scripts/init_db.py

python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Windows 启动器提供的建库、切库、测试连接、升级数据库、启停与日志查看能力，在 Linux 与 macOS 上需要分别使用 `scripts/init_db.py`、`alembic upgrade head`、systemd 或其他进程管理工具替代。
